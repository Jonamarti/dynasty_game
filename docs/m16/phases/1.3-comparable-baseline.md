## Goal

Three tools every later phase uses: a machine-readable matrix result, a diff
between two of them, and a test that pins the checkpoint fingerprint of seeds
1–3 so any unintended world change is caught (R13).

## Files

`tools/scenarios.ts`; new `tools/baseline-diff.ts`; new
`src/sim/__tests__/switches-off.test.ts`; new `fixtures/switches-off.json`;
new `tools/baseline-pin.ts`; `package.json` (scripts);
`src/sim/persistence/CheckpointRecords.ts` (read only: `toCheckpointRecord`,
~l. 187).

## Steps

1. `tools/scenarios.ts`: add `--json <path>`. For each scenario write
   `{ name, passed: string[], failed: string[], na: string[] }`.
2. `tools/baseline-diff.ts` + script `baseline:diff`:
   `npm run baseline:diff -- before.json after.json` prints, per scenario,
   the checks that went pass→fail, pass→n/a, fail→pass, n/a→pass. Exit code 1
   if any pass→fail or pass→n/a.
3. `switches-off.test.ts`: for seeds `'1'`, `'2'`, `'3'` with the `band`
   scenario's config, build a `Simulation`, run 3,000 steps with every M16
   switch **off** (none exist yet: the default config), call
   `toCheckpointRecord(sim)`, hash it (stable key-ordered JSON + FNV-1a in a
   small helper; no new dependency) and compare with `fixtures/switches-off.json`.
4. `baseline:pin` script regenerates `fixtures/switches-off.json`. Put a
   comment at the top of the test: "Re-pin only when a phase changes the
   world on purpose, and say so in the commit (`docs/m16/README.md` §5)."
5. Save the matrix JSON of the current build as
   `artifacts/verification/m16-baseline/matrix.json`.

## Tests

- The new test passes.
- R17: change one constant in `Brain.ts` by hand (e.g. a score weight), run
  the test, see it fail, restore.
- `baseline:diff` of a file against itself exits 0; against a hand-edited copy
  with one pass→fail it exits 1.

## Done when

All three tools exist and are in `package.json`, and the R17 check was done
(mention it in the diary).

## Watch out

If 3 × 3,000 steps takes more than ~20 s inside the unit suite, give the test
an explicit timeout with a comment (T3 rule); do not shorten the run.
Tooling only: no version bump.
