## Goal

`toCheckpointRecord(sim)` works for every scenario a fixture recipe (1.5) will
use, so fixture worlds can be built from them.

## Background (checked on 0.15.160)

The checkpoint codec is strict: `CheckpointRecords.ts:42` rejects a config
with "unknown or missing fields". The scenarios `hearths`, `porters`,
`scribes` and `conquest` put keys into their config (or via `setup`) that the
codec does not accept (`bugs.md`, "fase 29c: semillas y fuentes", audit of
06-10). The only migration so far is for `otherBandThinkInterval`
(`CheckpointRecords.ts:71-76`) — use it as the model for any migration here.

## Steps

1. Write `src/sim/__tests__/m16-scenarios-checkpointable.test.ts`: for each
   scenario in `SCENARIOS`, build it, run its `setup` if any, step 10 times,
   and assert that `toCheckpointRecord(sim)` and then
   `Simulation.fromCheckpointRecord(...)` succeed. Run it; list the failing
   scenarios with their exact error.
2. For each offending key decide, and write in the diary which you chose:
   - a real simulation `Config` field the codec forgot → add it to the codec
     with a migration (R23) that sets the old default when absent;
   - a harness-only key (not simulation state) → move it out of the config in
     `tools/simcheck.ts` so the simulation never sees it.
3. Never relax the strict check itself.

## Tests

The new test passes for every scenario, or the remaining failures are in
`docs/m16/doubts.md` with the reason (R0).

## Done when

`hearths`, `porters`, `scribes`, `conquest` (and any other) checkpoint and
reload; `switches-off.test.ts` still passes.

## Watch out

A migration must not change what an existing save loads as: old saves load
exactly as before.
